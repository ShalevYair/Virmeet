# Virmeet

כלי לסימולציית פגישה עם פרסונות ארגוניות. בוחרים משתתפים, מגדירים את מטרת
הפגישה, מעלים חומרי רקע — והסוכנים מקיימים דיון שמסתיים בתמליל ובמשימות לביצוע.

> הפלט של הכלי הוא **הכנה לפגישה, לא תחליף לה**. הדעות שנוצרות כאן הן פלט של
> מודל שפה ואינן מייצגות את עמדתם של אנשים אמיתיים.

---

## מה הכלי בעצם עושה

הערך אינו ב"תמלול פגישה מדומה" אלא בשאלה **מה יישאל בפגישה האמיתית ואין עליו
תשובה**. לכן הפלט המרכזי הוא שאלות פתוחות והתנגשויות בין אינטרסים; המשימות הן
מה שנגזר מהן.

המנגנון שמייצר את זה הוא **א-סימטריית ידע**: לכל פרסונה הפרומט שלה, הקבצים שלה,
וה-KPI שעליו היא נמדדת. אם כולן רואות את אותו הקשר, מקבלים ארבעה עותקים של אותו
מודל שמתחזים לארבעה אנשים.

## התקנה והרצה

```bash
npm install
cp .env.example .env.local     # והזן ANTHROPIC_API_KEY
npm run dev                    # http://localhost:3000
```

בהרצה הראשונה נוצרות אוטומטית תחת `data/` פרסונות ברירת מחדל (ארכיטקט תשתיות,
ארכיטקט תוכנה, מנמ"ר, מנהל פרויקט), חמישה סוגי מטרת פגישה, והגדרות ארגון
לדוגמה — הכל ניתן לעריכה מלאה מתוך הממשק.

```bash
npm run typecheck   # tsc --noEmit
npm run build
```

## מפתח ה-API של Anthropic

יש שתי דרכים להזין מפתח, ואפשר להשתמש בכל אחת מהן בנפרד. הדרך הראשונה היא
`ANTHROPIC_API_KEY` בקובץ `.env.local`, כמו למעלה — זה מפתח שרת-כלל, שרץ בצד
השרת ותקף לכל מי שמריץ פגישה מול המופע הזה. הדרך השנייה היא להדביק מפתח אישי
במסך ההגדרות (`/settings`); הוא נשמר ב-`localStorage` של הדפדפן ונשלח לשרת רק
בבקשת ההרצה עצמה (`POST /api/meetings/[id]/run`, כותרת `x-anthropic-api-key`),
בלי לגעת בדיסק, בתמליל, או בלוגים. אם קיימים שני המפתחות, המפתח מהדפדפן גובר.

חשוב להבין את המשמעות של האופציה השנייה: `localStorage` נגיש לכל סקריפט שרץ
בדף הזה, כך שהיא מתאימה למכשיר אישי שרק אתם משתמשים בו, ולא למופע חשוף לרשת או
משותף בין כמה משתמשים — שם המפתח היחיד שאמור להיות מוגדר הוא `ANTHROPIC_API_KEY`
בצד השרת.

## מכונת המצבים של הפגישה

הפגישה אינה round-robin חופשי. היא מכונת מצבים דטרמיניסטית, וה-LLM פועל רק
בתוך שלב:

| שלב | מה קורה |
|---|---|
| `prep` | כל פרסונה קוראת את חומרי הרקע **בנפרד ובמקביל**, ומייצרת הבנה, שלושה חששות ושלוש שאלות — לפני שהיא שומעת מישהו אחר |
| `opening` | המנחה מקבל את כל פלטי ההכנה ומזהה 2־4 התנגשויות ממוקדות בין העמדות |
| `discussion` | N סבבים (1־4). בכל סבב כל פרסונה מגיבה למה שנאמר בפועל, סביב ההתנגשויות |
| `convergence` | המנחה מסכם: מה סוכם, מה נשאר פתוח, מי צריך להחליט |
| `extraction` | חילוץ `MeetingResult` מובנה — משימות, החלטות, שאלות פתוחות, סיכונים |

**שלב `prep` מבודד בכוונה.** זה מה שמונע עדריות: פרסונה שכבר שמעה את דעת המנמ"ר
תתיישר אליה. אל "תייעל" את השלב הזה להקשר משותף — זה מפרק את הכלי.

שתי החלטות עיצוב נוספות שנובעות מאותו שיקול:

- כל פרסונה מורשית במפורש לומר *"אין לי את המידע הזה, צריך לבדוק מול X"*. זו
  תשובה מוצלחת, לא כישלון. בלי ההיתר הזה מתקבל מסמך יפה ומופרך.
- כל משימה נושאת את **ההנחה שעליה היא נשענת** ואת **מה קורה אם ההנחה שגויה**,
  וכל מה שהמודל השלים בעצמו מרוכז בשדה נפרד (`modelAssumptions`).

### עמידות

- כשל של פרסונה בודדת אינו מפיל את הפגישה — נרשמת שורת מערכת בתמליל והדיון ממשיך.
- לכל פרסונה תקציב קריאות (`maxApiCalls`); בחריגה היא מדולגת בסבבים הבאים.
- הפגישה נשמרת לדיסק אחרי כל שלב, כך שקריסה אינה מוחקת את התמליל.
- כשל בשלב `extraction` מסמן את הפגישה כ-`failed` אבל **התמליל נשמר**.

## מבנה

```
src/
  app/
    api/                 12 קבוצות routes (REST + SSE)
    meetings/            אשף פגישה חדשה, רשימה, מסך הרצה ותוצאות
    personas/            רשימת משתתפים ועורך משתתף
    meeting-types/       ניהול סוגי מטרות פגישה
    settings/            הגדרות ארגון
  components/            רכיבי UI משותפים
  lib/
    engine/              מכונת המצבים: prompts, schemas, budget, runner
    anthropic.ts         עטיפה לקריאת מודל: caching, retry, חיפוש רשת, refusal
    store.ts             אחסון קבצי JSON עם כתיבה אטומית ונעילה per-file
    extract.ts           חילוץ טקסט מקבצים
    seed.ts              נתוני ברירת מחדל
data/                    נתוני ריצה — לא בגיט
```

הרצת הפגישה משודרת ללקוח ב-SSE מ-`POST /api/meetings/[id]/run`. צורות האירועים:

```
{type:'phase',     phase}
{type:'entry',     entry}
{type:'done',      result}
{type:'error',     message}
{type:'cancelled'}
```

`cancelled` נפלט כשהמשתמש ביטל את הפגישה (`PATCH /api/meetings/[id]` עם
`status:'cancelled'`) — הריצה נבדקת מול ה-store בראש כל שלב ולפני כל תור
בדיון, כך שהיא נעצרת תוך תור אחד לכל היותר, גם אם הבקשה מטופלת בתהליך אחר.
השורה `: ping` שנשלחת כל 15 שניות היא heartbeat ל-SSE (לא אירוע `data:`) —
הלקוח מתעלם ממנה.

### שאלות המשך אחרי הפגישה

`POST /api/meetings/[id]/ask` (גוף `{personaId, question}`) — שאלה חד-פעמית
לפרסונה (או `personaId:'facilitator'`) על פגישה שכבר `completed`, קריאת מודל
בודדת מחוץ למכונת המצבים, באותם בלוקי `system` שהפרסונה השתמשה בהם בפגישה
עצמה (כדי לשמור על ה-voice ועל ה-cache). התשובות נשמרות ב-`Meeting.followUps[]`
ונספרות לתוך `usage` הכולל של הפגישה. פגישות שנוצרו לפני התוספת הזו לא מכילות
את השדה — כל קריאה חייבת להתייחס אליו כ-`meeting.followUps ?? []`.

## מגבלות ידועות

- **אין אימות משתמשים ואין הרשאות.** הכלי מיועד להרצה מקומית, לא לחשיפה ברשת.
- **האחסון הוא קבצי JSON על הדיסק**, לא בסיס נתונים. מתאים למשתמש יחיד.
- **אין RAG.** קבצי הרקע נדחפים ישירות להקשר של הפרסונה. זה מכוון — retrieval
  מוסיף שכבת כשל שתסתיר את השאלה האמיתית, האם הפרסונות בכלל נשמעות שונה. הוא
  יתווסף כשגודל הקורפוס יאלץ את זה.
- **אין זיכרון בין פגישות.** כל פגישה מתחילה מאפס.
- חילוץ טקסט מ-PDF ומ-DOCX הוא best-effort; כשל בחילוץ מסומן על הקובץ ואינו
  מפיל את ההעלאה.

`npm test` מריץ את בדיקות היחידה (vitest — שכבת הלוגיקה בלבד, בלי jsdom):
תקציב קריאות, אחסון (עסקאות מקבילות, קבצים פגומים, העלאות), מכונת המצבים
(כולל ביטול ותקרת עלות), בוני הפרומטים, ייצוא, ותרגום שגיאות ולידציה
לעברית. `npm run test:watch` להרצה בזמן פיתוח.

## איך לדעת אם הכלי עובד

קריטריון ההצלחה הוא לא "יצא תמליל משכנע". קח פרוטוקול של פגישה אמיתית שכבר
התקיימה, הזן לכלי **רק את מה שהיה זמין לפניה**, והשווה: כמה מהסוגיות שעלו בפועל
הכלי העלה מראש, וכמה ממה שהעלה היה רעש.

אם הוא מייצר עשרים תובנות שכולן נכונות־אך־מובנות־מאליהן, זה מחולל טקסט ולא כלי.

בדיקה זולה נוספת לאיכות הפרסונות: הרץ פגישה, ערבב את השורות, ובקש ממודל אחר
לשייך כל אמירה לדובר. אם הוא לא עובר את רמת הניחוש — הפרסונות פיקטיביות, וצריך
להקצין את האינטרסים ואת א-סימטריית הידע.

**הבדיקה הזו ממומשת:**

```bash
npm run eval:personas -- <meetingId>
```

טוען פגישה קיימת (לפי ה-id שמופיע בכתובת ה-URL שלה, `/meetings/<meetingId>`),
לוקח את כל שורות שלב `discussion`, מסתיר כל שם דובר, מערבב את הסדר, ומבקש
מ-Opus לשייך כל אמירה בחזרה למשתתף — בפלט מובנה. מדפיס דיוח בעברית: דיוק כולל
ולכל פרסונה בנפרד, מטריצת בלבול (אילו שתי פרסונות מתערבבות זו בזו), ופסק דין
מול קו הבסיס של ניחוש אקראי (`1/מספר המשתתפים`):

- **ציון עובר:** דיוק של לפחות **פי 1.5** מקו הבסיס. מתחת לזה, הפרסונות אינן
  נבדלות באמת.
- ריצה על פגישה שבה כל המשתתפים קיבלו בכוונה את אותו פרומפט אמורה להחזיר ציון
  קרוב לקו הבסיס (זו בדיקת התקינות של המדד עצמו).

הסקריפט רץ כקובץ TypeScript ישיר תחת Node (`node scripts/eval-distinctiveness.ts`,
תכונת type-stripping המובנית ב-Node 22 — בלי `ts-node`/`tsx` ובלי תלות חדשה),
וקורא מ-`ANTHROPIC_API_KEY` בסביבה בלבד (לא מ-`localStorage` של הדפדפן).
