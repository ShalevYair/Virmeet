# Virmeet

כלי לסימולציית פגישה עם פרסונות ארגוניות. בוחרים משתתפים, מגדירים את מטרת
הפגישה, מעלים חומרי רקע — והסוכנים מקיימים דיון שמסתיים בתמליל ובמשימות לביצוע.

**האתר החי:** `https://shalevyair.github.io/Virmeet/` (מתעדכן אוטומטית בכל push
ל-`main` — ראו "פריסה" למטה).

> הפלט של הכלי הוא **הכנה לפגישה, לא תחליף לה**. הדעות שנוצרות כאן הן פלט של
> מודל שפה ואינן מייצגות את עמדתם של אנשים אמיתיים.

Virmeet הוא **אתר סטטי לחלוטין**: אין שרת, אין בסיס נתונים, ואין דיסק. כל
הנתונים חיים ב-`IndexedDB` של הדפדפן שלכם, וכל קריאה למודל (Gemini) יוצאת
**ישירות מהדפדפן** אל ה-API. ראו "מודל האמון" למטה לפני שמזינים מפתח API.

## מה הכלי בעצם עושה

הערך אינו ב"תמלול פגישה מדומה" אלא בשאלה **מה יישאל בפגישה האמיתית ואין עליו
תשובה**. לכן הפלט המרכזי הוא שאלות פתוחות והתנגשויות בין אינטרסים; המשימות הן
מה שנגזר מהן.

המנגנון שמייצר את זה הוא **א-סימטריית ידע**: לכל פרסונה הפרומט שלה, הקבצים שלה,
וה-KPI שעליו היא נמדדת. אם כולן רואות את אותו הקשר, מקבלים ארבעה עותקים של אותו
מודל שמתחזים לארבעה אנשים.

## התקנה והרצה מקומית

```bash
npm install
npm run dev                    # http://localhost:3000
```

`predev`/`prebuild` (רצים אוטומטית) סורקים את `public/seed/` ומייצרים את
`public/seed/manifest.json` — הקובץ שהדפדפן קורא כדי לדעת אילו פרסונות וסוגי
פגישות קיימים (אי אפשר לרשום תוכן תיקייה מהדפדפן). אל תערכו את `manifest.json`
ידנית, הוא ב-`.gitignore` ונוצר מחדש בכל הרצה.

בכניסה ראשונה בדפדפן, 4 פרסונות ברירת מחדל (ארכיטקט תשתיות, ארכיטקט תוכנה,
מנמ"ר, מנהל פרויקט), חמישה סוגי מטרת פגישה, והגדרות ארגון לדוגמה נטענים
אוטומטית מ-`public/seed/` לתוך ה-`IndexedDB` של הדפדפן — הכל ניתן לעריכה מלאה
מתוך הממשק, ועריכה מקומית **לעולם לא נדרסת** בכניסה חוזרת (ראו "הוספת פרסונה
דרך GitHub" למטה).

```bash
npm run typecheck   # tsc --noEmit
npm test            # vitest run
npm run lint        # eslint .
npm run build       # מייצא לתיקיית out/ (output: 'export')
```

## פריסה ל-GitHub Pages

`.github/workflows/deploy-pages.yml` בונה ופורס אוטומטית בכל push ל-`main`.
בהגדרות הריפו: **Settings → Pages → Source: GitHub Actions**. ה-workflow
מריץ `npm run build` עם `NEXT_PUBLIC_BASE_PATH=/Virmeet` (כדי שהאתר יעבוד
מתת-הנתיב שבו GitHub Pages מגיש אותו) ומעלה את `out/`.

אפשר לפרוס את אותו build הסטטי גם ל-Vercel/Netlify/כל אחסון סטטי אחר, בלי
שינוי — פשוט לא להגדיר `NEXT_PUBLIC_BASE_PATH` (או להגדיר לפי הנתיב שלכם שם).

## הוספת פרסונה או קובץ רקע דרך GitHub

אפשר להוסיף/לערוך פרסונות וסוגי פגישות **בלי לגעת בקוד**, ישירות דרך ממשק
הדפדפן של GitHub:

1. הוסיפו קובץ JSON תחת `public/seed/personas/<id>.json` (מבנה השדות ב-
   `src/lib/seed-schemas.ts`, `personaSeedSchema`) — או ערכו קובץ קיים.
2. להוספת קובץ רקע: העלו אותו ל-`public/seed/files/` (ראו את ה-README שם),
   והוסיפו את הנתיב היחסי שלו למערך `files` בתוך ה-JSON של הפרסונה.
3. Commit + push ל-`main`. ה-Action ירוץ, ייצור מחדש את `manifest.json`,
   ויפרוס. תוך דקות הפרסונה/הקובץ יופיעו אצל כל מי שנכנס לאתר (משתמשים
   קיימים יראו אותם אחרי שה-`seedVersion` המקומי שלהם יתעדכן — קורה אוטומטית,
   או מיידית דרך "טען מחדש מהריפו" בעמוד ההגדרות).

## מודל האמון — מפתח ה-API של Gemini

הכלי מבוסס כולו על Gemini (`@google/genai`) — אין תלות בספק מודלים אחר. בעת
יצירת פגישה חדשה בוחרים מודל אחד מבין שלוש רמות (`/meetings/new/`): Gemini
Pro (הכי חזק), Gemini Flash (מאוזן, ברירת מחדל), Gemini Flash-Lite (הכי מהיר
וזול) — כינויים קבועים שמוגדרים ב-`AVAILABLE_MODELS` ב-`src/lib/types.ts`.
המודל הנבחר משמש את כל המשתתפים ואת המנחה באותה פגישה; אין הגדרת מודל נפרדת
לכל פרסונה.

**אין שרת, ולכן אין אופציה של מפתח בצד שרת.** מזינים מפתח אישי במסך ההגדרות
(`/settings/`); הוא נשמר ב-`localStorage` של הדפדפן, **על המכשיר הזה בלבד**,
ונשלח **ישירות מהדפדפן** אל ה-API של Gemini בזמן הרצת הפגישה — בלי לעבור דרך
שום שרת. יש גם כפתור "בדוק תקינות" שמאמת את המפתח מול ה-API האמיתי (בקשת
רשימת מודלים — לא צורכת טוקנים) לפני שמתחילים להשתמש בו.

זה מודל האמון של **כלי אישי**, לא של שירות רב-משתמשים:

- `localStorage` נגיש לכל סקריפט שרץ בדף הזה. מתאים למכשיר האישי שלכם, **לא**
  למחשב משותף או ציבורי.
- המפתח חשוף בקוד הצד-לקוח (Network tab, DevTools) בזמן שהפגישה רצה — זה
  בלתי נמנע כששולחים בקשה ישירות מהדפדפן לספק.

## חיבור ל-Google Drive — ידע לפרסונות (אופציונלי)

במסך ההגדרות (`/settings/`) אפשר לחבר תיקיית Google Drive שממנה כל פרסונה
שואבת קבצי רקע פרטיים משלה, בנוסף לקבצים שמעלים ידנית. OAuth כולו בדפדפן
(Google Identity Services), בלי שרת.

**בניגוד למפתח ה-Gemini, ה-Client ID הוא לא סוד אישי של המשתמש** — הוא מזהה
את **האתר עצמו**, ומוגדר פעם אחת על ידי מריץ האתר (ולא דרך הממשק). כתוצאה
מזה, מסך ההגדרות מציג רק כפתור אחד — **"התחבר ל-Drive"** — שמריץ את חלון
ה-OAuth של גוגל (אישור עם חשבון Google של המשתמש) **ומקים את מבנה
התיקיות אוטומטית** מיד אחרי החיבור, בלי שלב נוסף. אם ה-Client ID לא הוגדר
באתר, הכפתור נעלם ומוצגת הודעה על כך במקומו.

- **אסימון הגישה נשמר בזיכרון הדפדפן בלבד** (לא ב-`localStorage`) — קצר-טווח
  (כשעה), נעלם בסגירת/רענון הלשונית, ודורש התחברות מחדש בכל פעם.
- ה-scope המבוקש הוא **גישה מלאה ל-Drive** (`.../auth/drive`), לא ה-scope
  המצומצם `drive.file` — כי המנגנון צריך לראות קבצים שנוספו ידנית דרך
  Drive, לא רק קבצים שהאתר עצמו יצר. המשמעות: מסך ה-consent ב-Google Cloud
  יכול להישאר במצב "Testing" הבלתי-מאומת — אין צורך בתהליך אימות/בדיקת
  אבטחה מול Google כל עוד זה שימוש אישי/למשתמשים מוגדרים מראש (עד 100 test
  users).

### הגדרת ה-Client ID (למריץ האתר בלבד)

צריך OAuth Client ID **אחד** לכל האתר (לא לכל משתמש). ליצירתו:

1. נכנסים ל-[Google Cloud Console](https://console.cloud.google.com/) ויוצרים
   פרויקט חדש (או בוחרים קיים).
2. **APIs & Services → Library** → מחפשים "Google Drive API" → **Enable**.
3. **APIs & Services → OAuth consent screen** → סוג "External" → ממלאים שם
   אפליקציה ואימייל תמיכה → נשארים במצב "Testing" ומוסיפים את עצמכם (ואת מי
   שעוד ישתמש) כ-"Test users". אין צורך בתהליך אימות מול גוגל לשימוש אישי.
4. **APIs & Services → Credentials → Create Credentials → OAuth client ID**
   → סוג "Web application" → תחת "Authorized JavaScript origins" מוסיפים:
   - `http://localhost:3000` (לפיתוח מקומי)
   - `https://shalevyair.github.io` (לאתר הפרוס — **בלי** `/Virmeet` בסוף,
     רק המקור/origin)
5. יוצרים, ומעתיקים את ה-Client ID שנוצר (נראה כמו
   `xxxxxxxxxxxx-yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy.apps.googleusercontent.com`).

איפה שמים את הערך:

- **פיתוח מקומי:** בקובץ `.env.local` בשורש הריפו (נוצר אוטומטית עם placeholder
  ריק, לא נכנס ל-git) — `NEXT_PUBLIC_DRIVE_CLIENT_ID=<הערך שהעתקתם>`.
- **האתר הפרוס (GitHub Pages):** ב-GitHub, **Settings → Secrets and
  variables → Actions → Variables → New repository variable**, שם
  `NEXT_PUBLIC_DRIVE_CLIENT_ID`, ערך — אותו Client ID. לא Secret (זה לא
  סודי) — Variable רגיל. ה-workflow (`deploy-pages.yml`) כבר מוגדר לקרוא
  אותו אוטומטית בבנייה הבאה.
- **בתחילת כל פגישה**, לכל משתתף עם תיקיית Drive מחוברת, המנוע מרענן את
  אינדקס הידע שלו: סורק את התיקייה, ומשווה כל קובץ מול קובץ אינדקס
  (`_virmeet-index.md`) שנשמר בתוך אותה תיקייה ב-Drive — שם וזמן עדכון לכל
  קובץ. קובץ שלא השתנה לא נקרא מחדש; קובץ חדש/שהשתנה נקרא (`extract.ts`)
  ומסוכם במשפט־שניים על ידי Gemini Flash-Lite (`gemini-3.5-flash-lite`
  קבוע — בלי קשר למודל שנבחר לפגישה עצמה), והתקציר נשמר חזרה לאינדקס.
  מוגבל ל-20 קבצים חדשים/משתנים לריצה אחת (`MAX_FILES_TO_SUMMARIZE_PER_RUN`
  ב-`engine/drive-knowledge.ts`) — אותו עיקרון "תקצוב לכל דבר" כמו
  `maxApiCalls`/`maxWebSearches`. כשל ברענון עבור פרסונה בודדת (למשל אין
  חיבור פעיל) נרשם כשורת מערכת בתמליל ולא מפיל את הפגישה.
- **התקציר של כל קובץ מוזרק לפרומפט של הפרסונה** מתחילת שלב `prep` ואילך —
  תחת "קבצי ידע זמינים ב-Drive". תקציר בלבד, לא התוכן המלא (שמירה על עלות
  נמוכה כברירת מחדל).
- בשלב `prep` עצמו, כחלק מהפלט המובנה (יחד עם understanding/concerns/
  questions), כל פרסונה יכולה לבקש **לקרוא לעומק** עד 3 קבצים מהאינדקס שלה
  (`filesToReadInDepth`) — לא live tool-calling תוך כדי דיון (ראו את שיקול
  העיצוב למעלה תחת "מכונת המצבים"), אלא החלטה מפורשת כחלק מפלט ה-JSON
  הקיים של שלב ההכנה. מיד אחרי שכל הפרסונות סיימו prep, המנוע מוריד ומחלץ
  את הקבצים המבוקשים בפועל (`extract.ts`) ומזריק אותם — התוכן המלא הפעם —
  לכל הקריאות הנותרות של אותה פרסונה באותה פגישה (`opening` ואילך). קובץ
  שלא נמצא באינדקס (שם שגוי/הזיה של המודל) פשוט מדולג בשקט.

קוד: `src/lib/drive.ts` (קריאות REST ל-Drive v3, כולל רמת קבצים — רשימה,
הורדה, יצירה/עדכון), `src/lib/drive-auth.ts` (טעינת GIS + זרימת ה-OAuth),
`src/lib/drive-session.ts` (החזקת האסימון בזיכרון),
`src/components/DriveSettings.tsx` (הממשק), `src/lib/engine/drive-knowledge.ts`
(רענון האינדקס וקריאה לעומק — פורמט, דיפ, סיכום, חילוץ).

## מכונת המצבים של הפגישה

הפגישה אינה round-robin חופשי. היא מכונת מצבים דטרמיניסטית, וה-LLM פועל רק
בתוך שלב:

| שלב | מה קורה |
|---|---|
| `prep` | לפני הקריאות המקבילות: אינדקס הידע ב-Drive של כל משתתף מחובר מתרענן (ראו "חיבור ל-Google Drive" למעלה). אז כל פרסונה קוראת את חומרי הרקע **בנפרד ובמקביל**, ומייצרת הבנה, שלושה חששות, שלוש שאלות, ורשימת קבצי Drive (אם יש) שהיא מבקשת לקרוא לעומק — לפני שהיא שומעת מישהו אחר. מיד אחרי, המנוע מוריד את הקבצים המבוקשים ומזריק אותם (תוכן מלא) לשאר קריאות אותה פרסונה |
| `opening` | המנחה מקבל את כל פלטי ההכנה ומזהה 2־4 התנגשויות ממוקדות בין העמדות |
| `discussion` | N סבבים (1־4). בכל סבב כל פרסונה מגיבה למה שנאמר בפועל, סביב ההתנגשויות. אם `meeting.creatorParticipates`, יוצר הפגישה מקבל תור נוסף בסוף כל סבב, אחרי כל הפרסונות |
| `convergence` | המנחה מסכם: מה סוכם, מה נשאר פתוח, מי צריך להחליט |
| `extraction` | חילוץ `MeetingResult` מובנה — משימות, החלטות, שאלות פתוחות, סיכונים — וגם כותרת לפגישה עצמה (`meeting.title`, שנשאר ריק עד השלב הזה; אין שדה כותרת ידני ביצירת פגישה) |

**שלב `prep` מבודד בכוונה.** זה מה שמונע עדריות: פרסונה שכבר שמעה את דעת המנמ"ר
תתיישר אליה. אל "תייעל" את השלב הזה להקשר משותף — זה מפרק את הכלי.

שתי החלטות עיצוב נוספות שנובעות מאותו שיקול:

- כל פרסונה מורשית במפורש לומר *"אין לי את המידע הזה, צריך לבדוק מול X"*. זו
  תשובה מוצלחת, לא כישלון. בלי ההיתר הזה מתקבל מסמך יפה ומופרך.
- כל משימה נושאת את **ההנחה שעליה היא נשענת** ואת **מה קורה אם ההנחה שגויה**,
  וכל מה שהמודל השלים בעצמו מרוכז בשדה נפרד (`modelAssumptions`).
- משימה שהמודל לא הצליח לשייך לבעלים ברור מהדיון משויכת אוטומטית ל**מנהל
  הפרויקט**, ולא נשארת ללא בעלים (`resolveTaskOwnerName` ב-`engine/runner.ts`).

### עמידות

- כשל של פרסונה בודדת אינו מפיל את הפגישה — נרשמת שורת מערכת בתמליל והדיון ממשיך.
- לכל פרסונה תקציב קריאות (`maxApiCalls`); בחריגה היא מדולגת בסבבים הבאים.
- הפגישה נשמרת לדיסק אחרי כל שלב, כך שקריסה אינה מוחקת את התמליל.
- כשל בשלב `extraction` מסמן את הפגישה כ-`failed` אבל **התמליל נשמר**, וגם
  פגישה כזו וגם פגישה שבוטלה ניתנות להרצה מחדש (כפתור "הרץ שוב" בעמוד הפגישה).

## מבנה

```
src/
  app/
    meetings/            אשף פגישה חדשה, רשימה, מסך הרצה (/meetings/view/?id=) ותוצאות
    personas/            רשימת משתתפים ועורך משתתף (/personas/edit/?id=)
    meeting-types/       ניהול סוגי מטרות פגישה
    settings/            הגדרות ארגון, מפתחות API, "טען מחדש מהריפו"
  components/            רכיבי UI משותפים (כולל SeedBoot — טעינת seed באתחול)
  lib/
    engine/              מכונת המצבים: prompts, schemas, budget, runner
    eval/                מדדי הערכה (למשל eval-attribution — ראו npm run eval:attribution)
    gemini.ts            עטיפת דפדפן ל-Gemini: callModel(), thinking, grounding, retry, refusal
    store.ts             אחסון ב-IndexedDB (idb) — אותן חתימות פונקציות כמו הגרסה הישנה מול דיסק
    extract.ts           חילוץ טקסט בדפדפן (pdf.js + mammoth browser build)

    drive.ts              קריאות REST ל-Google Drive v3 (יצירת/איתור תיקיות)
    drive-auth.ts          זרימת OAuth מול Drive (Google Identity Services, בדפדפן בלבד)

```

הפגישה רצה **בתוך הדפדפן**, ישירות מ-`runMeeting()` במנוע — אין SSE ואין
network hop. `runMeeting(id, handlers)` ב-`lib/api-client.ts` קורא למנוע
ומעביר callback; חוזה האירועים זהה לגרסה הקודמת:

```
{type:'phase',   phase}
{type:'entry',   entry}
{type:'done',    result}
{type:'error',   message}
```

## מגבלות ידועות

- **הנתונים חיים בדפדפן בלבד (IndexedDB).** החלפת מחשב, החלפת דפדפן, או ניקוי
  נתוני אתר — והכל נעלם. ייצוא פרסונה ל-JSON הוא מנגנון הגיבוי היחיד לפרסונות.
- **המפתח חשוף בדפדפן.** ראו "מודל האמון" למעלה.
- **הריצה קשורה ללשונית פתוחה.** סגירה/ניווט החוצה באמצע ריצה עוצר אותה — יש
  אזהרת `beforeunload` בזמן ריצה. פגישה שנשארה תקועה ב-`running` (למשל אחרי
  סגירת הלשונית באמצע ריצה) מזוהה אוטומטית אחרי כמה דקות בלי עדכון: מופיע
  באנר בעמוד הפגישה, ומשם אפשר לבטל אותה דרך כפתור "בטל פגישה" ואז להריץ
  מחדש.
- **אין שיתוף בין משתמשים.** שני אנשים שגולשים לאותו URL לא רואים אותם נתונים.
- **אין RAG.** קבצי הרקע נדחפים ישירות להקשר של הפרסונה. זה מכוון — retrieval
  מוסיף שכבת כשל שתסתיר את השאלה האמיתית, האם הפרסונות בכלל נשמעות שונה.
- **אין זיכרון בין פגישות.** כל פגישה מתחילה מאפס.
- חילוץ טקסט מ-PDF ומ-DOCX הוא best-effort; כשל בחילוץ מסומן על הקובץ ואינו
  מפיל את ההעלאה.
- **כיסוי בדיקות חלקי.** `npm test` (vitest) מכסה: תקציב קריאות (`budget`),
  ביטול כולל אות abort (`cancel`, `gemini`), טיפול
  בקטיעת תשובה (`truncation`), חישוב `usage` כולל `cacheWriteTokens`
  (`usage`), מדד ייחוס דוברים (`attribution`), ושכבת ה-API (`api-client`) —
  כולל שערי המעברים בין סטטוסים. **ללא כיסוי:** `store.ts`, `prompts.ts`,
  `extract.ts`, `export.ts`, `seed-loader.ts` (כולל `isSafeSeedRelativePath`,
  בדיקת אבטחת נתיב).

### הדרך חזרה לגרסת שרת

הגרסה הסטטית לא סוגרת את הדלת: התג `pre-static-rewrite` שומר את גרסת ה-Next.js
עם צד שרת (routes תחת `src/app/api/`, אחסון ב-`data/`) כפי שהייתה לפני ההסבה,
לשחזור אם ירצו בעתיד אחסון משותף בצד שרת.

## איך לדעת אם הכלי עובד

קריטריון ההצלחה הוא לא "יצא תמליל משכנע". קח פרוטוקול של פגישה אמיתית שכבר
התקיימה, הזן לכלי **רק את מה שהיה זמין לפניה**, והשווה: כמה מהסוגיות שעלו בפועל
הכלי העלה מראש, וכמה ממה שהעלה היה רעש.

אם הוא מייצר עשרים תובנות שכולן נכונות־אך־מובנות־מאליהן, זה מחולל טקסט ולא כלי.

בדיקה זולה נוספת לאיכות הפרסונות: הרץ פגישה, ערבב את השורות, ובקש ממודל אחר
לשייך כל אמירה לדובר. אם הוא לא עובר את רמת הניחוש — הפרסונות פיקטיביות, וצריך
להקצין את האינטרסים ואת א-סימטריית הידע.

בדיקה זו ממומשת כלי פיתוח נפרד, מחוץ לחבילת האפליקציה: השלם פגישה, לחץ
"ייצוא JSON" במסך הפגישה, והרץ `npm run eval:attribution -- <קובץ-שיוצא>.json`
(דורש `GEMINI_API_KEY` בסביבה). התוצאה: דיוק שיוך מול רמת הניחוש האקראית
(1/מספר המשתתפים), פירוט recall/precision לכל משתתף, ומטריצת בלבול.
