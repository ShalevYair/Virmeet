## שלב 1 — רשת ביטחון: lint ו-CI

**למה קודם:** כרגע אין linting בכלל, ואין CI שמריץ בדיקות. כל שינוי בשלבים
הבאים נכנס בלי שום שער אוטומטי. זה השלב הזול ביותר וחסר הסיכון המוצרי היחיד.

### 1.1 להחזיר את `npm run lint` לחיים

**הראיה:** `npm run lint` מריץ `next lint`, שמדפיס אזהרת deprecation ואז נופל
לאשף אינטראקטיבי ("How would you like to configure ESLint?") ומחזיר exit 1. אין
`eslint` ב-`devDependencies` של `package.json`, ואין קובץ קונפיג של ESLint ב-repo
(אימות: `ls -a | grep -i eslint` מחזיר ריק). במקביל `next.config.ts` מגדיר
`eslint: { ignoreDuringBuilds: true }` — כלומר גם ה-build לא בודק כלום. עם זאת
בקוד יש כבר `// eslint-disable-next-line react-hooks/exhaustive-deps`
(`view/page.tsx:445`) שמניח שיש linter.

**מה לעשות:**

1. הוסף `eslint` ו-`eslint-config-next` ל-`devDependencies`. **אמת את הגרסאות
   התואמות ל-Next 15.5.22 שמותקן** (`npm info eslint-config-next@15.5.22`) — אל
   תנחש מספרי גרסה.
2. צור קונפיג flat (`eslint.config.mjs`) שמרחיב את `next/core-web-vitals`.
   `next lint` הוסר ב-Next 16, אז אל תישאר עליו: החלף את הסקריפט ל-ESLint CLI:
   ```json
   "lint": "eslint ."
   ```
3. הוסף ל-ignore של הקונפיג: `.next/`, `out/`, `node_modules/`, `public/`.
4. הרץ פעם אחת וראה מה נופל. **אל תשתיק חוקים כדי לעבור.** אם חוק מייצר רעש
   אמיתי — תעד למה בהערה ליד הכיבוי. אם הוא מייצר ממצא אמיתי — תקן אותו, אבל
   **בקומיט נפרד** מהקומיט שמקים את התשתית.
5. השאר את `eslint: { ignoreDuringBuilds: true }` ב-`next.config.ts` כמו שהוא —
   ה-lint ירוץ ב-CI כשלב נפרד, ואין סיבה להאט את ה-build של הפריסה.

**קריטריון סיום:** `npm run lint` רץ **בלי אינטראקטיביות** ומחזיר exit 0.
בדוק במפורש שהוא לא תלוי ב-TTY: `npm run lint < /dev/null`.

### 1.2 CI שמריץ את מה שקיים

**הראיה:** `.github/workflows/` מכיל קובץ אחד בלבד — `deploy-pages.yml` — שעושה
`npm ci` → `npm run build` → deploy, ורץ רק על push ל-`main`. **23 הבדיקות שנוספו
ב-PR #5 לא רצות אוטומטית אף פעם**, וגם `tsc --noEmit` לא.

**מה לעשות:** צור `.github/workflows/ci.yml`:

- טריגר: `pull_request` ו-`push` (לכל ענף), ו-`workflow_dispatch`.
- `permissions: contents: read` בלבד.
- job אחד, `ubuntu-latest`, Node 20 עם `cache: npm` (עקוב אחרי הסגנון של
  `deploy-pages.yml` — אותה גרסת Node, אותן פעולות).
- שלבים, בסדר הזה: `npm ci` → `npm run typecheck` → `npm test` → `npm run lint`
  → `npm run build`.
- הוסף `concurrency` לפי `github.ref` עם `cancel-in-progress: true`, כדי
  ש-push רצוף לא יצבור ריצות.

**שים לב:** `npm run build` מפעיל אוטומטית `prebuild` (בניית `manifest.json`
והעתקת ה-worker של pdf.js). אל תוסיף אותם ידנית ואל תסיר את הקריאה.

**קריטריון סיום:** ה-workflow ירוק על ענף העבודה. ודא שהוא באמת מריץ את
הבדיקות (הסתכל בלוג של השלב, לא רק בעיגול הירוק).

## שלב 2 — הרצה חוזרת: להפעיל תיקון שכבר קיים

### 2.1 הבאג

זה הממצא החמור ביותר בסקירה, והוא לא באג בקוד אלא **פיצ'ר שמומש ואי אפשר להגיע
אליו**.

`api-client.ts:377-380` מאפס `transcript` ו-`usage` לפני הרצה חוזרת — בדיוק
ההמלצה (ב) של `PLAN-correctness-and-evaluation.md §7.1`, שמומשה ב-PR #11
(`605de55`). ההערה מעליו (שורות 370-376) מסבירה את הכוונה במפורש.

אבל **שום מקום ב-UI לא מפעיל הרצה חוזרת:**

- `view/page.tsx:396` — ההרצה האוטומטית מותנית ב-`m.status === 'draft'`.
- אין כפתור "הרץ שוב" באף עמוד.
- אימות: `grep -rn "status: 'draft'" src/app src/components` מחזיר רק קריאות
  `useState` והשוואות — **אף רכיב לא כותב `'draft'` בחזרה לאחסון.**

התוצאה: פגישה שהסתיימה ב-`failed` או ב-`cancelled` היא מבוי סתום. הפעולה היחידה
שנשארה עליה בעמוד הרשימה (`meetings/page.tsx:116-122`) היא מחיקה. קוד האיפוס
ב-`api-client.ts` הוא, בפועל, קוד מת.

### 2.2 התיקון

**א. שער בשכבת ה-API.** ב-`meetingsApi.update` (`api-client.ts:234-260`) יש כבר
שער נגד ביטול פגישה שהושלמה (שורה 243), אבל **אין שער נגד החזרת פגישה שהושלמה
ל-`draft`** — וזה מסלול שיאפשר למחוק תוצאות של פגישה מוצלחת. הוסף:

```ts
if (patch.status === 'draft' && meeting.status === 'completed') {
  badRequest('לא ניתן להריץ מחדש פגישה שכבר הושלמה. שכפל אותה במקום.');
}
```

(`MeetingUpdateInput.status` כבר מוגדר כ-`'draft' | 'cancelled'` בשורה 207, אז
אין שינוי טיפוס.)

**ב. חילוץ לוגיקת ההתחלה ב-`view/page.tsx`.** כרגע ההתחלה מוטמעת בתוך ה-`.then`
של ה-effect (שורות 396-429). חלץ אותה ל-`startRun()` שאפשר לקרוא לה משני
מקומות — מה-effect ומהכפתור החדש.

**ג. כפתור "הרץ שוב".** הצג אותו כש-`status === 'failed' || status === 'cancelled'`,
לצד כפתורי הייצוא באזור ב-`view/page.tsx:513-537`.

**ד. — הקריטי — לאפס גם את ה-state המקומי.**

זו המלכודת המרכזית בסעיף הזה. `api-client.runMeeting` מאפס את התמליל **באחסון**,
אבל `applyMeeting` (`view/page.tsx:359-370`) כבר טען את התמליל הישן ל-state
המקומי, ו-`onEntry` רק מוסיף (`setTranscript((prev) => [...prev, entry])`,
שורה 404). בלי איפוס מקומי, המשתמש יראה את התמליל הישן **ואחריו** את החדש —
כפילות שלא קיימת באחסון. לפני קריאה ל-`runMeeting` בהרצה חוזרת, אפס:

```ts
setTranscript([]);
setResult(null);
setRunError(null);
setCurrentPhase('prep');
```

**ה. `hasStartedRef`.** הוא מונע הרצה כפולה מה-effect (`view/page.tsx:348,397`).
הכפתור לא עובר דרך ה-effect, אז הוא לא חסום על ידו — אבל **כן** צריך למנוע
לחיצה כפולה: הוסף מצב `starting` שמשבית את הכפתור בזמן שההרצה מתחילה.

**ו. `AbortController` חדש.** `abortRef.current` מחזיק את ה-controller של הריצה
הקודמת, שכבר בוטל. הרצה חוזרת חייבת ליצור `new AbortController()` ולהחליף את
ה-ref — אחרת הריצה החדשה מתחילה עם signal שכבר במצב aborted ותיעצר מיד.

### 2.3 בדיקות

הוסף ל-`src/lib/api-client.test.ts`:
- החזרת פגישה `completed` ל-`draft` נחסמת עם `ApiError`.
- החזרת פגישה `failed` ל-`draft` מצליחה.
- החזרת פגישה `cancelled` ל-`draft` מצליחה.

**קריטריון סיום:** פגישה שבוטלה באמצע → "הרץ שוב" → התמליל בממשק מתחיל מאפס
(לא מצטבר), ו-`usage` באחסון מתחיל מ-0. אמת ב-DevTools → Application → IndexedDB.

## שלב 3 — תיקוני נכונות ממוקדים

### 3.1 מזהה מודל לא מוכר מנותב בשקט ל-Anthropic

**הראיה:** `getModelProvider` (`types.ts:19-21`) מחזיר `'anthropic'` לכל מחרוזת
שאינה ברשימת `GEMINI_MODELS`. במסך עריכת הפרסונה יש `<select>` סגור
(`personas/edit/page.tsx:245-262`), אז מהממשק אי אפשר לטעות. אבל:

- `seed-schemas.ts:20` מאמת `model: z.string().min(1)` בלבד.
- `persona-io.ts:73,91` (ייבוא פרסונה מ-JSON) מעביר את הערך כמו שהוא.

פרסונה שנטענת מ-`public/seed/` או מיובאת מ-JSON עם `"model": "gemini-2.0-flash"`
(מזהה שלא ברשימה) תנותב ל-Anthropic. **וגרוע מכך:** בדיקת המפתחות המקדימה
ב-`api-client.ts:356-368` משתמשת באותה `getModelProvider`, אז היא תיתן אישור
שגוי ("יש מפתח Anthropic, הכל בסדר") — והכשל יתגלה רק כשכל קריאה של הפרסונה
תיכשל באמצע הפגישה.

**התיקון (מינימלי, בלי לשבור נתונים קיימים):**

1. ב-`types.ts`, ליד `getModelProvider`, הוסף:
   ```ts
   /** True iff `model` is one of the ids this app actually knows how to route (see AVAILABLE_MODELS). */
   export function isKnownModel(model: string): boolean {
     return (AVAILABLE_MODELS as readonly string[]).includes(model);
   }
   ```
2. ב-`api-client.ts`, בבדיקה המקדימה (סביב שורה 359), הוסף בדיקה נפרדת
   **לפני** בדיקת המפתחות: משתתפים עם `!isKnownModel(p.model)` נחסמים עם הודעה
   עברית מפורשת שמציינת את שם המשתתף ואת מזהה המודל הלא-מוכר, ומפנה למסך עריכת
   המשתתף. אל תמזג אותם לרשימת `blockedParticipants` הקיימת — ההודעה שם ("דרוש
   מפתח API שלא הוגדר") תהיה מטעה.

**למה לא להדק את `personaSeedSchema` ל-`z.enum`:** זה יגרום לפרסונת seed עם
מודל לא מוכר להיכשל בטעינה, ו-`seed-loader.ts:219` רק כותב `console.warn` —
כלומר הפרסונה תיעלם בשקט מהממשק. זו החלפה של כשל רועש בכשל שקט. אם בכל זאת
רוצים אימות בשכבת הסכימה, זה שינוי נפרד שדורש גם טיפול נראה-למשתמש בכשל טעינה,
והוא לא בסקופ כאן.

**בדיקות:** הוסף ל-`api-client.test.ts` מקרה של משתתף עם `model: 'not-a-model'`
→ ההרצה נחסמת לפני קריאת מודל כלשהי.

### 3.2 טוקני כתיבה ל-cache לא נספרים

**הראיה:** `anthropic.ts:119-125` (`usageFrom`) קורא רק `input_tokens`,
`output_tokens` ו-`cache_read_input_tokens`. **`cache_creation_input_tokens` לא
נקרא כלל.** כתיבה ל-cache מחויבת ביוקר יותר מקלט רגיל, והיא בדיוק מה שקורה
בקריאה הראשונה של כל פגישה — אחרי ש-PR #4 העביר את הקבצים המשותפים לבלוקים
ממוקשים (`prompts.ts:75-97`).

**למה זה חשוב מעבר לדיוק:** `PLAN-file-context-optimization.md §3` מגדיר את
`usage` ככלי המדידה שלפיו מחליטים אם שלב 2 (תמציות) בכלל מוצדק. כלי המדידה הזה
כרגע עיוור לצד אחד של המשוואה.

**התיקון:**

1. `llm-types.ts` — הוסף `cacheWriteTokens: number` ל-`CallModelUsage`
   (שורות 34-38).
2. `anthropic.ts:119` — `cacheWriteTokens: usage.cache_creation_input_tokens ?? 0`.
3. `gemini.ts:71-77` — ל-Gemini אין מקבילה (ה-caching שלו implicit). החזר `0`,
   **עם הערה בקוד שמסבירה שזה מכוון ולא השמטה.**
4. `types.ts:124` — הוסף `cacheWriteTokens: number` ל-`Meeting['usage']`.
5. `store.ts:299` — הוסף `cacheWriteTokens: 0` לאתחול ב-`createMeeting`.
6. `api-client.ts:379` — הוסף `cacheWriteTokens: 0` לאיפוס בהרצה חוזרת.
7. `runner.ts:197-204` (`recordTokens`) — הוסף את השדה.
8. `runner.ts:150` — **המלכודת.** `usage = { ...meeting.usage }` קורא רשומה
   שנשמרה ב-IndexedDB לפני השינוי הזה, ושאין בה `cacheWriteTokens`. אז
   `undefined + n === NaN`, וכל המונה נהרס. חייבים ברירת מחדל:
   ```ts
   let usage = { cacheWriteTokens: 0, ...meeting.usage };
   ```
   בדוק את אותה בעיה בכל מקום אחר שקורא `meeting.usage` ומחבר אליו.

**אין צורך להעלות `DB_VERSION`.** כפי ש-`PLAN-file-context-optimization.md §5.1`
כבר קובע: IndexedDB לא אוכף סכימה ברמת הרשומה, והוספת שדה אופציונלי לא דורשת

## שלב 4 — לראות מה זה עולה

### 4.1 הבעיה

`Meeting.usage` נצבר בקפידה לאורך כל הריצה (`runner.ts:193-204`) ונשמר אחרי כל
שלב — **ולא מרונדר באף עמוד.** אימות:
`grep -rn "usage" src/app src/components` מחזיר **אפס תוצאות**.

המשתמש שורף מפתח API אישי משלו בעיוורון מוחלט. הדרך היחידה לראות מספרים היא
"ייצוא JSON", שזמין רק כש-`status === 'completed' && result`
(`view/page.tsx:519`) — כלומר דווקא על פגישה שנכשלה, זו שסביר שבזבזה הכי הרבה,
אין שום גישה למספרים.

### 4.2 התיקון

**א. פאנל שימוש בעמוד הפגישה.** הוסף ל-`view/page.tsx` כרטיס שמציג:
`apiCalls`, `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheWriteTokens`
(האחרון מסעיף 3.2).

- הצג אותו בכל סטטוס שאינו `draft` — כולל `failed` ו-`cancelled`. זו כל הנקודה.
- בזמן ריצה הוא צריך להתעדכן. ה-state המקומי לא מחזיק `usage` (רק
  `transcript`/`status`/`result`), אז יש שתי אפשרויות: להוסיף `usage` ל-state
  ולעדכן מתוך `entry.usage` בכל `onEntry`, או לרענן מהאחסון. **בחר את הראשונה** —
  `TranscriptEntry.usage` כבר קיים (`types.ts:86`) ומאוכלס
  (`runner.ts:281-282,417-418`), ואין צורך בקריאת IndexedDB נוספת בכל שורה.
  שים לב: שורות `system` הן בלי `usage`, וקריאות המנחה נספרות ב-`usage` הכולל
  אבל **לא** נושאות `usage` על ה-entry (`runner.ts:331-338,459`) — כלומר
  הסכימה מ-entries בלבד תהיה חסרה. לכן: קרא `usage` מהאחסון בכל מעבר שלב
  (יש כבר `onPhase`), ואל תנסה לשחזר אותו מהתמליל.

**ב. שימוש בייצוא ה-Markdown.** הוסף סעיף `## שימוש` ל-`renderMarkdown`
(`export.ts:73-119`), אחרי בלוק הסטטוס. **אל תיגע ב-disclaimer ובסדר הקיים
של שאר הסעיפים** — הם חלק מהחוזה של הייצוא.

**ג. לאפשר ייצוא של פגישה שלא הושלמה.** כרגע כפתורי הייצוא מותנים ב-`completed`
(`view/page.tsx:519`). הרחב ל-`completed | failed | cancelled`.
`renderMarkdown` כבר מטפל ב-`meeting.result === null` (שורה 87) וב-`meeting.error`
(שורה 81), אז אין שינוי נדרש שם. זה גם מה שהופך את המדידה שדורשת
`PLAN-file-context-optimization.md §3` לאפשרית בפועל.

**הערכת עלות בכסף — לא כאן.** ראה סעיף 9.1. הצגת מספרי טוקנים היא עובדה
שנמדדה; המרה למחיר דורשת טבלת תמחור שמשתנה עם הזמן ואסור להמציא אותה מהזיכרון.

**קריטריון סיום:** פגישה שבוטלה באמצע שלב הדיון מציגה מונה קריאות וטוקנים שאינו
אפס, וניתנת לייצוא ל-Markdown ול-JSON.

## שלב 5 — ביטול שבאמת מפסיק

> **זה השלב היחיד שנוגע בחוזה המשותף של שני הספקים.** כל שינוי ב-`llm-types.ts`

### 5.1 הבאג

PR #6 (`f3fbe28`) תיקן את "ביטול לא מבטל" — אבל רק חלקית, וזה מתועד בקוד עצמו:
`abortIfCancelled` (`runner.ts:183-191`) נבדק רק **בין** קריאות מודל, וההערה
בשורות 177-182 מתארת בדיוק את זה ("stops at the next checkpoint").

מה שלא מטופל: **`CallModelOptions` (`llm-types.ts:21-32`) לא כולל `signal` כלל.**
אימות: `grep -rn "signal\|abort" src/lib/anthropic.ts src/lib/gemini.ts
src/lib/llm.ts src/lib/llm-types.ts` מחזיר **אפס תוצאות**. כלומר קריאה שכבר
יצאה לספק ממשיכה עד סופה, ומחויבת במלואה, אחרי שהמשתמש לחץ "בטל".

התרחישים הגרועים:
- **שלב `prep`** (`runner.ts:216-235`) — כל המשתתפים רצים ב-`Promise.allSettled`.
  הביטול ממתין לסיום **כולם**.
- **לולאת ה-retry** — `sleep(2000/4000/8000)` (`anthropic.ts:172`,
  `gemini.ts:140`) לא מודעת לביטול. עד 14 שניות המתנה סרק לכל קריאה, ואז
  הקריאה החוזרת עדיין יוצאת.

הבדיקה הידנית ש-`PLAN-correctness-and-evaluation.md §8` דורשת ("שבלשונית Network
לא יוצאות קריאות נוספות אחרי הביטול") עוברת — אבל היא בודקת קריאות **חדשות**,
לא כאלה שכבר באוויר.

### 5.2 מה ה-SDK-ים תומכים בו — מאומת ב-`node_modules`, לא משוער

| Gemini | `abortSignal` **בתוך `config`** | `genai.d.ts` — `GenerateContentConfig.abortSignal?: AbortSignal` |

שים לב להבדל: אצל Anthropic זה ארגומנט נפרד, אצל Gemini זה שדה בתוך אובייקט

### 5.3 התיקון

1. **`llm-types.ts`** — הוסף ל-`CallModelOptions`:
   ```ts
   /** Aborts the in-flight provider request and any pending retry backoff. */
   signal?: AbortSignal;
   ```
2. **`anthropic.ts:155-176`** — העבר `{ signal: opts.signal }` כארגומנט השני
   לשתי הקריאות (`create` ו-`stream`).
3. **`gemini.ts:86-143`** — הוסף `config.abortSignal = opts.signal` (רק אם

4. **`sleep()` בשני הקבצים** (`anthropic.ts:31-33`, `gemini.ts:26-28`) — הפוך
   אותה למודעת ביטול: תדחה (או תחזור מוקדם) כשה-signal נדלק, במקום להמתין
   את כל הזמן. הסר את המאזין ב-`finally` כדי לא לדלוף listeners על signal
   שחי לאורך כל הפגישה.
5. **`llm.ts:10-12`** — לא דורש שינוי (הוא מעביר את `opts` כמו שהוא), אבל ודא.
6. **`runner.ts`** — העבר `signal` לכל אחת מחמש קריאות `deps.callModel`
   (שורות 220, 296, 377, 442, 483).
7. **— הקריטי —** `runner.ts:422-429`: כשקריאה נכשלת, ה-`catch` כותב
   `personaErrorLine` לתמליל. אחרי השינוי, ביטול יגרום לכל הקריאות שבאוויר
   לדחות עם `AbortError`, וייכתבו שורות שגיאה מזויפות לתמליל לפני שורת הביטול.
   **הוסף בדיקת `isAborted()` לפני כתיבת שורת השגיאה** ודלג עליה כשהריצה בוטלה.
   אותו דבר בטיפול ב-`prepAttempts` שנדחו (`runner.ts:245-250`) ובשלבי המנחה

## 9. החלטות פתוחות — דורשות אישור הבעלים לפני מימוש

### 9.1 הערכת עלות בכסף (משלים את שלב 4)

עצירה נקייה עם חילוץ, או עצירה מיידית? **תלוי בשלב 4** — בלי תצוגת שימוש אין
דרך למשתמש להבין למה הפגישה נעצרה.

### 9.3 שאלות המשך ודיון מונחה-מנחה

## 10. אימות סופי

```bash
npm run typecheck
npm test
npm run lint          # חייב לרוץ לא-אינטראקטיבי ולהחזיר 0
npm run build         # חייב לעבור עם output:"export" — כל route חדש ישבור אותו
```

**ובדיקות ידניות שאף בדיקה אוטומטית לא מכסה:**

1. **הרצה חוזרת (שלב 2):** הרץ פגישה עם 2 פרסונות ו-2 סבבים, בטל באמצע הדיון,
   לחץ "הרץ שוב". ודא ב-DevTools → Application → IndexedDB שהתמליל התחיל מאפס
   ושה-`usage` אופס — **וגם שהתמליל בממשק לא מציג את הריצה הישנה והחדשה יחד.**
2. **ביטול אמיתי (שלב 5):** בטל באמצע שלב `prep` עם 4 משתתפים. הריצה צריכה
   להיעצר תוך שנייה-שתיים, הבקשות בלשונית Network צריכות להיות `canceled`,
   ובתמליל **לא** אמורות להופיע שורות שגיאה לפני שורת הביטול.
3. **תצוגת שימוש (שלב 4):** פגישה שבוטלה מציגה מונה טוקנים שאינו אפס וניתנת
   לייצוא ל-Markdown ול-JSON.
4. **`usage` ישן (סעיף 3.2):** פגישה שנוצרה **לפני** השינוי ורצה **אחריו** לא
   מציגה `NaN` באף מונה.
