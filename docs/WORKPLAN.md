## 1. רקע — מה האפליקציה עושה

Virmeet היא סימולציית פגישה רב-משתתפים. בוחרים פרסונות ארגוניות, מגדירים מטרת
פגישה, מעלים חומרי רקע — והסוכנים מקיימים דיון שמסתיים בתמליל, במשימות, בשאלות
פתוחות ובהתנגשויות.

**הערך אינו התמליל.** הערך הוא זיהוי מוקדם של *מה יישאל בפגישה האמיתית ואין עליו
תשובה*. המנגנון שמייצר את זה הוא **א-סימטריית ידע** בין הפרסונות.

## 2. אילוצים ועקרונות עבודה

## 3. חוזי ליבה שאסור לשבור

אלה החלטות עיצוב מכוונות. שינוי שלהן מפרק את הכלי, גם אם הוא "מייעל" אותו.

### 3.1 שלב `prep` מבודד

כל פרסונה קוראת את החומרים **בלי לראות אף פרסונה אחרת** (`runner.ts:163-182`).
זה מה שמונע עדריות. **אין להפוך את `prep` להקשר משותף, ואין להריץ אותו סדרתית עם
העברת פלט בין פרסונות.**

### 3.2 יציבות בלוקי ה-system לצורך prompt caching

עבור כל פרסונה, `system` הוא תמיד בדיוק
`[orgBlock, personaPrompt, personaFilesBlock]` ואף אחד מהם אינו משתנה במהלך
הריצה (`prompts.ts:69-75`). `cache_control` יושב על הבלוק האחרון בלבד
(`anthropic.ts:91-98`). **אין להכניס תוכן פר-שלב או פר-סבב לתוך בלוקי ה-system.**

### 3.3 ההיתר לומר "אין לי את המידע"

`prompts.ts:46-49` מגדיר במפורש שהודאה בפער ידע היא תשובה מוצלחת. **אין להסיר או
להחליש את הפסקה הזו.** בלעדיה מתקבל מסמך משכנע ומופרך.

### 3.4 הפרדת הנחות המודל

`MeetingResult.modelAssumptions` + `assumption`/`riskIfAssumptionWrong` על כל
משימה (`types.ts:66-86`). **אין למזג אותם לתוך `summary`.**

### 3.5 גילוי נאות

הבאנר "הפלט הזה הוא הכנה לפגישה, לא תחליף לה…" מופיע במסך התוצאות
(`meetings/[id]/page.tsx:56-80`) ובראש כל ייצוא Markdown
(`export/render.ts:8`, מילה במילה). **חייב להישאר בשני המקומות, וכל פורמט ייצוא
חדש חייב לכלול אותו.**

### 3.6 מפתח API אישי לא נוגע בדיסק

מפתח מהדפדפן מגיע בכותרת `x-anthropic-api-key` בבקשת ההרצה בלבד, מועבר ל-
`callModel`, ואף פעם לא נכנס ל-`meeting`, לתמליל, ללוגים או ל-`data/`
(`run/route.ts:19-24`, `runner.ts:80-85`, `anthropic.ts:16-31`).
**כל קוד חדש שנוגע במפתח חייב לשמור על זה.**

# שלב 1 — יציבות ריצה ובקרת ביטול (P0)

> ללא השלב הזה, "בטל" לא מבטל כלום, ופגישה שנתקעה אבודה לצמיתות.

## P1.1 — ביטול פגישה אמיתי

**הבעיה.** `handleCancel` (`meetings/[id]/page.tsx:446-459`) עושה `abort` ל-fetch
ו-`PATCH status:'cancelled'`. אבל:

- `runMeeting` לא בודק את סטטוס הפגישה אף פעם — אין קריאה חוזרת ל-store בלולאות.
- `cancel()` ב-SSE route (`run/route.ts:68-73`) מתעד במפורש שהריצה ממשיכה בשרת.
- `emitPhase` עושה `persist({status:'running'})` (`runner.ts:137-140`) ודורס את
  ה-`cancelled` תוך שניות.
- שלב `extraction` מסיים ב-`status:'completed'` (`runner.ts:449`).

**התוצאה:** המשתמש רואה "בוטלה", השרת ממשיך לשרוף את כל ~21 הקריאות, והפגישה
מסתיימת כ"הושלמה".

**קבצים.** `src/lib/engine/runner.ts`, `src/lib/anthropic.ts`,
`src/lib/engine/types.ts`, `src/lib/api-client.ts`,
`src/app/meetings/[id]/page.tsx`, `src/app/api/meetings/[id]/run/route.ts`

**מה לעשות.**

1. ב-`runner.ts`, להוסיף בדיקת ביטול שנשענת על ה-store (סמכותית, שורדת גם ריצה
   בכמה תהליכים):

   ```ts
   async function isCancelled(): Promise<boolean> {
     const fresh = await deps.getMeeting(meetingId);
     return fresh?.status === 'cancelled';
   }
   ```

2. לבדוק אותה: בראש כל שלב, ולפני כל תור בלולאת הדיון
   (`runner.ts:295-296`). בביטול — לרשום שורת מערכת בתמליל, לשמור
   `{status:'cancelled'}`, לפלוט אירוע ביטול, ולחזור מהפונקציה.
3. **לתקן את `persist`/`emitPhase`** כך שלא ידרסו `cancelled`: `emitPhase` יכתוב
   `status:'running'` רק אם הסטטוס הנוכחי אינו `cancelled`.
4. להוסיף `AbortController` ברמת הריצה ולהעביר `signal` דרך `CallModelOptions`
   אל `client.messages.create(params, { signal })` — כדי לקטוע גם קריאה שכבר
   באוויר, לא רק למנוע את הבאה.
5. להרחיב את חוזה האירועים ב-`engine/types.ts` ב-`{ type: 'cancelled' }`,
   ולטפל בו ב-`api-client.ts` (`RunEvent`, `RunMeetingHandlers.onCancelled`)
   ובמסך ההרצה. **זו הרחבה מכוונת של החוזה — לעדכן את התיעוד ב-README בהתאם.**
6. ה-route: לשמור מיפוי `meetingId -> AbortController` ברמת המודול, כדי ש-`PATCH`
   לביטול יוכל לקטוע ריצה שרצה באותו תהליך מיידית, בלי להמתין לבדיקה הבאה.

**קריטריוני קבלה.**

- לחיצה על "בטל פגישה" באמצע שלב הדיון עוצרת את הריצה תוך תור אחד לכל היותר.
- לאחר הביטול, `data/meetings/<id>.json` נשאר עם `status:'cancelled'` — גם דקה
  אחרי, וגם אחרי רענון הדף.
- `usage.apiCalls` מפסיק לגדול אחרי הביטול.
- התמליל שנצבר עד הביטול נשמר במלואו.
- שורת מערכת בעברית בתמליל: "הפגישה בוטלה על ידי המשתמש."

## P1.2 — Timeout על קריאות מודל

**הבעיה.** `callModel` (`anthropic.ts:172-193`) עושה retry על
`RateLimitError`/`InternalServerError`/`APIConnectionError`, אבל **אין timeout**.
אם חיבור נתלה, השלב תלוי לנצח והפגישה נתקעת ב-`running` לצמיתות (ראו P1.3).

**קבצים.** `src/lib/anthropic.ts`, `src/lib/engine/runner.ts`

**מה לעשות.**

1. להוסיף `timeoutMs?: number` ל-`CallModelOptions`, עם ברירת מחדל של 180
   שניות (`const DEFAULT_TIMEOUT_MS = 180_000`).
2. להעביר אותו כ-request option של ה-SDK:
   `client.messages.create(params, { timeout: timeoutMs, signal })`.
3. לוודא ש-timeout נחשב **שגיאה שניתן לנסות שוב** (הוא מגיע כ-
   `Anthropic.APIConnectionTimeoutError`) — להוסיף אותו ל-`isRetryableError`.
4. `errorMessage()` ב-runner צריך להפיק הודעה בעברית לשורת המערכת בתמליל, לא את
   הטקסט הגולמי של ה-SDK. להוסיף מיפוי שגיאות → הודעות עברית.

**קריטריוני קבלה.**

- קריאה שנתקעת מעל הסף נכשלת, עוברת retry, ובסופו מייצרת שורת מערכת בעברית —
  והפגישה ממשיכה לשלב הבא במקום להיתקע.
- ניתן להגדיר timeout שונה לכל קריאה (שלב `extraction` עם תמליל ארוך עשוי לדרוש
  יותר).

## P1.3 — התאוששות מפגישה תקועה ב-`running`

**הבעיה.** אם התהליך נופל באמצע ריצה, `status` נשאר `running` על הדיסק לנצח:

- ה-UI נכנס ל-`startPolling` אינסופי (`meetings/[id]/page.tsx:423-427`).
- `POST /run` מחזיר 409 "הפגישה כבר רצה כעת" (`run/route.ts:28-30`).
- אין reaper, אין בדיקת liveness, אין כפתור.

**קבצים.** `src/app/api/meetings/[id]/run/route.ts`,
`src/app/meetings/[id]/page.tsx`, `src/lib/types.ts`

**מה לעשות.**

1. להגדיר סף התיישנות: `const STALE_RUN_MS = 5 * 60_000`. פגישה נחשבת תקועה אם
   `status === 'running'` וגם `Date.now() - Date.parse(updatedAt) > STALE_RUN_MS`.
   `updatedAt` מתעדכן אחרי כל ערך בתמליל (`store.ts:414-421`), ולכן הוא אות
   חיוּת סביר.
2. `POST /run` יאפשר הרצה כאשר הסטטוס `draft`, `failed`, `cancelled`, או
   `running` שהתיישן. להשאיר את החסימה על `completed`.
3. בהרצה חוזרת — לאפס לפני `runMeeting`:
   `{ transcript: [], result: null, error: null, completedAt: null,
      usage: {inputTokens:0, outputTokens:0, cacheReadTokens:0, apiCalls:0} }`.
   (הרצה חוזרת מייצרת פגישה חדשה, לא ממשיכה תמליל קיים.)
4. ב-UI: כפתור **"הרץ שוב"** שמוצג כאשר הסטטוס `failed`/`cancelled`/`running`
   מיושן. לפניו `ConfirmDialog` שמסביר שהתמליל הקיים יימחק.

**קריטריוני קבלה.**

- הריגת השרת באמצע ריצה, הפעלה מחדש, כניסה לעמוד הפגישה → מוצג "הרצה קודמת
  הופסקה" וכפתור "הרץ שוב" פעיל.
- פגישה שנכשלה בשלב `extraction` ניתנת להרצה חוזרת מה-UI.
- פגישה `completed` לא ניתנת להרצה חוזרת (מחזירה 409).

## P1.4 — Heartbeat ל-SSE

**הבעיה.** שלב `prep` עם 4 פרסונות וחיפוש רשת יכול לקחת דקות בלי לפלוט אף
אירוע. כל reverse proxy סביר סוגר חיבור SSE שקט אחרי 30–60 שניות.

**קבצים.** `src/app/api/meetings/[id]/run/route.ts`

**מה לעשות.** להוסיף `setInterval` כל 15 שניות שכותב שורת הערה של SSE:
`controller.enqueue(encoder.encode(': ping\n\n'))`, ולנקות אותו ב-`finally`
וב-`cancel()`.

**הערה חשובה.** הפרסר בצד הלקוח (`api-client.ts:230-250`) מחפש שורה שמתחילה ב-
`data:` ומדלג על השאר — שורת `: ping` בטוחה ולא דורשת שינוי בלקוח.

**קריטריוני קבלה.** חיבור SSE נשאר פתוח לאורך שלב `prep` ארוך מ-60 שניות, גם
מאחורי proxy.

## P1.5 — ולידציית `objective` בצד הלקוח + שמות שדות בעברית

**הבעיה (א).** `formValid` באשף הפגישה החדשה
(`meetings/new/page.tsx:83`) הוא `titleValid && typesValid && participantsValid`
— **`objective` לא נבדק**, אבל השרת דורש `z.string().min(1)`
(`api/_lib/schemas.ts:39`).

**הבעיה (ב).** משתמש שמשאיר את השדה ריק מקבל:
`השדה "objective" קטן מדי, קצר מדי, או ריק.` — שם שדה באנגלית בתוך משפט עברי,
באפליקציה שכולה RTL. `fieldLabel` (`api/_lib/http.ts:14-16`) מחזיר את מפתח ה-JSON
הגולמי, בניגוד להערה בראש הקובץ שמבטיחה הודעות עבריות בלבד.

**קבצים.** `src/app/meetings/new/page.tsx`, `src/app/api/_lib/http.ts`

**מה לעשות.**

1. להוסיף `objectiveValid = objective.trim().length > 0` ל-`formValid`, עם הודעת

## P4.3 — שיפור פגיעת ה-cache בשלב הדיון

**הבעיה.** ההערה בראש `prompts.ts` נכונה לגבי בלוקי ה-system — אבל **רוב הטוקנים
הם ב-user message, והוא אינו cached**. גרוע מכך:
`buildDiscussionUserMessage` שם את מספר הסבב **לפני** התמליל
(`prompts.ts:204`: `# מה נאמר עד כה (סבב ${round} מתוך ${totalRounds})`), מה ששובר
את ה-prefix המשותף בין סבב לסבב ומונע כל פגיעת cache על החלק הכבד.

**קבצים.** `src/lib/engine/prompts.ts`, `src/lib/anthropic.ts`

**מה לעשות.**

1. לסדר מחדש את הודעת הדיון כך שהחלק היציב יהיה קידומת רציפה: כותרת הפגישה →
   מסגור → התנגשויות → **תמליל** → (רק בסוף) הוראת המשימה עם מספר הסבב.
2. לאפשר `cache_control` גם על בלוק בהודעת ה-user: להרחיב את `CallModelOptions`
   כך שאפשר להעביר את התמליל כבלוק תוכן נפרד עם breakpoint.
3. **לא לגעת בבלוקי ה-system** (§3.2).
4. למדוד: `cacheReadTokens` לפני ואחרי, על אותה פגישה עם אותם נתונים.

**קריטריוני קבלה.** `usage.cacheReadTokens` בפגישה של 4 משתתפים × 3 סבבים גדל
משמעותית מול המצב הקיים. לתעד את המספרים ב-commit message.

## P4.4 — ביצועי `listMeetings`

**הבעיה.** `listMeetings(true)` קורא ומפרסר **כל קובץ פגישה במלואו** — כולל

# שלב 8 — דיון מונחה-מנחה (ניסיוני)

> **לבצע רק אחרי שלב 7**, כי בלי מדד אין דרך לדעת אם השינוי שיפר או הרס.

**הבעיה.** לולאת הדיון היא round-robin נוקשה — כל פרסונה מדברת בכל סבב, בסדר קבוע
(`runner.ts:295-296`). סבבים 3–4 נוטים לחזרתיות: לכל אחד יש "תור" גם כשאין לו מה
לחדש, וכל תור עולה כסף.

**מה לעשות.**

1. בסוף כל סבב, קריאה קצרה למנחה שמחזירה תוכנית לסבב הבא בפלט מובנה: מי מדבר,
   ועל איזו התנגשות ספציפית הוא נדרש לענות.
2. `buildDiscussionUserMessage` יקבל שאלה ממוקדת במקום "זהו תורך לדבר".
3. פרסונה שהמנחה לא בחר בסבב מסוים — מדלגים עליה (ומתעדים זאת בתמליל, כדי
   שהמשתמש יבין למה היא שותקת).
4. **דגל תצורה** `discussionMode: 'round-robin' | 'facilitated'` על הפגישה, עם
   ברירת מחדל `round-robin`, כדי שאפשר יהיה להשוות את שני המצבים.

**קריטריוני קבלה.** השוואה על אותה פגישה בשני המצבים: פחות קריאות, וציון
distinctiveness (שלב 7) לא נמוך יותר.

**סיכון.** זה משנה את לב מכונת המצבים. אם המדד לא משתפר — לחזור אחורה, לא
"לתקן" בעוד שכבה.

אלה מגבלות מוכרות ומתועדות ב-README. **אין לטפל בהן בלי החלטה מפורשת** — לכל אחת
יש נימוק:

- **אין אימות משתמשים והרשאות.** הכלי מיועד להרצה מקומית. הוספת auth הופכת אותו
  למוצר אחר ודורשת החלטה מוצרית.

- **אין RAG.** קבצי הרקע נדחפים ישירות להקשר. זה מכוון: retrieval מוסיף שכבת
  כשל שתסתיר את השאלה האמיתית — האם הפרסונות בכלל נשמעות שונה. יתווסף כשגודל
  הקורפוס יאלץ.
- **אין זיכרון בין פגישות.** כל פגישה מתחילה מאפס.
- **חילוץ טקסט מ-PDF/DOCX הוא best-effort.** כשל מסומן על הקובץ ואינו מפיל את
  ההעלאה.
